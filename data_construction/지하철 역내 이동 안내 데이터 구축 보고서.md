# 지금까지의 작업 목적
지하철을 이용할 때 에스컬레이터를 최대한 활용해 이동할 수 있도록 안내하는 서비스를 만들기 위해, 역 내부의 세부 구조 데이터를 구축하고자 했다.
공공데이터에는 역 내부 동선 데이터가 존재하지 않기 때문에, 존재하는 관련된 부분 데이터(에스컬레이터, 빠른하차, 역사건축정보 등)를 조합하여 “탑승구별 이동 가능성”을 유추하는 방식으로 접근했다.

# 수행한 작업 
🔹 (1) 데이터 수집 및 정제

서울교통공사 에스컬레이터 설치 현황 데이터
→ 불필요한 컬럼 제거, 한글 컬럼명 정리, 내부/출구 에스컬레이터 분류(etype 생성).

서울교통공사 역사건축정보 데이터
→ 실제 승강장 층(B2, 1F 등)을 숫자(-2, 1)로 변환하여 탑승구_층.csv 생성.

빠른하차 API 데이터
→ 호선, 역명, 방면_탑승구, 탑승구_층, 승강장유형 등으로 정리 후 CSV 저장.

🔹 (2) 데이터 병합

승강기_일련번호를 기준으로
에스컬레이터 데이터(df_에스컬레이터) 와 빠른하차 데이터(df_빠른하차) 를 병합.

방면·탑승구 정보를 활용하여 양쪽 방면 데이터 보완 (섬식 승강장 한쪽만 기록된 문제 해결).

결과물: df_에스컬레이터_빠른하차_merge.csv

🔹 (3) 층수 변환 및 방향 판정 로직

pair_floor_to_num() 함수를 이용해 “지상/지하” + “층수” 정보를 숫자형으로 통일.

text_floor_to_num()으로 “B2, 3층, GF” 등의 텍스트를 일관된 숫자로 변환.

플랫폼 층(탑승구_층_num)과 에스컬레이터의 시작_층, 종료_층을 비교해
→ inbound(타러 가는 방향), outbound(내려서 나가는 방향) 을 판별.

오표기(층수 차이 오류) 보정을 위해 거리 기반 추론 + 단조성 규칙 적용.

결과물: 탑승구_판정.csv
(각 역의 방면·탑승구별로 “양방향 가능 / 들어오기만 가능 / 나가기만 가능 / 없음” 라벨링 완료)

# 해결된 문제
| 문제                     | 해결 방법                                    |
| ---------------------- | ---------------------------------------- |
| 승강장 유형이 한쪽 방면만 태깅됨     | 빠른하차 데이터의 양방향 방면 정보를 병합하여 보완             |
| 시작/종료 상세가 동일해 방향 식별 불가 | 플랫폼 층(`탑승구_층`)을 기준으로 inbound/outbound 구분 |
| 층 오표기(호선별 상대적 층수 표기)   | 플랫폼 기준 절댓값 비교 및 단조성 규칙으로 보정              |

이 과정을 통해,
“어느 방면의 몇 번 탑승구에서 에스컬레이터가 실제로 이용가능한지” 를 정확히 식별할 수 있게 되었다

# 한계점 및 결론
하지만, 현재 보유한 데이터로는 역 내부 전체 구조(출구–대합실–환승통로–승강장–탑승구) 의 정확한 연결 관계를 알 수 없다.

즉,

🚫 “에스컬레이터 기준으로 동선을 추론하는 것”은 한계가 있다.
✅ “역 구조 데이터를 기반으로 에스컬레이터를 보조적으로 활용해야 한다.”

이를 위해서는 역사 내 상세 구조 데이터(도면 수준) 가 필요하지만, 공공 데이터로는 “역 이용 안내도(이미지 형태)”만 제공되고 있으며 OCR로 추출하더라도 위치·층수·연결정보가 부정확하여 사람이 직접 보정해야 한다.

# 앞으로의 계획
- 우선 2호선 역을 기준으로, 역 이용 안내도(이미지) 를 참고해 수동으로 구조 데이터를 직접 구축한다.

    - 출구, 대합실, 환승통로, 승강장, 방면, 탑승구 노드 정의

    - 층 정보 및 연결 관계(에스컬레이터·계단·통로 등) 매핑

- 이후 이 구조 데이터를 기반으로 “출발역 → 환승역 → 도착역” 구간의 에스컬레이터 중심 안내 경로 생성 로직으로 확장할 예정이다.
